  2) SSE /api/web/events returns 503

  This is expected — API Gateway has a 29-second integration timeout and terminates long-lived SSE connections. Use the
  polling fallback instead:

  GET /api/web/events/poll
  Authorization: Bearer <token>

  This returns any pending events buffered in Redis and drains the queue. Poll every 3-5 seconds. Response:
  {
    "success": true,
    "content": {
      "events": [
        { "event": "generation.update", "data": {...}, "ts": 1716451200000 },
        { "event": "wallet.update", "data": {...}, "ts": 1716451201000 }
      ]
    }
  }

  Note: If /events/poll returns 404, it means the latest deployment hasn't been pushed yet. I'll verify this is deployed.

  3) PATCH /chat/{chatroomId}/settings does not update

  This was a real bug — fixed now. When you changed prompt-affecting settings (lust_level, response_length, language), it was
  wiping the conversation history from the LLM cache. The settings were saving correctly to DB/Redis, but the next AI message
  would lose all prior context, making it seem broken. Fix is ready to deploy.

  Usage:
  PATCH /api/web/chat/{chatroomId}/settings
  Authorization: Bearer <token>
  Content-Type: application/json

  {
    "lust_level": "flirty",           // friendly | flirty | steamy | intense
    "response_length": "long",        // short | medium | long
    "language": "spanish",            // any string
    "background_display": false,      // boolean (UI-only, no prompt rebuild)
    "allow_character_messages": true,  // boolean (UI-only)
    "model_preference": "premium"     // string, stored on chatContext
  }

  All fields are optional — send only what changed. Other settings are preserved (merge, not replace).

  To read settings back:
  GET /api/web/chat/{chatroomId}/settings
  Response: { content: { model_preference: "...", web_settings: { lust_level, response_length, language, background_display,
  allow_character_messages } } }

  4) Voice call has not been implemented

  It is implemented. The voice call works through the WebSocket, not a REST endpoint. Here's the flow:

  Step 1: Start chat
  POST /api/web/chat/start
  Body: { "character_id": "<uuid>" }
  → returns { chatroom_id }

  Step 2: Connect WebSocket
  wss://call.us-east-1.buzzs.me?token=<jwt_token>

  Step 3: Send voice message
  {
    "action": "web_voice_chat",
    "chatroomId": "<chatroom_id>",
    "userId": "<user_id>",
    "content": "Hello, how are you?",
    "voiceId": "en-US-AvaMultilingualNeural"
  }

  Step 4: Receive response
  - Text chunks: { "type": "chunk", "data": "hey" }
  - Audio frames: "A:<base64_mp3_data>"  (prefix "A:")
  - Audio end: { "type": "audio_end" }
  - Complete: { "type": "complete", "data": { "text": "full response" } }

  Available REST helpers:
  - GET /api/web/voice/list — list available voices (filter by ?gender=Female&isHd=true)
  - POST /api/web/voice/tts — one-shot text-to-speech (for previews)
  - POST /api/web/voice/call — initiate call (deducts credits, returns call metadata)

  I've E2E tested all of these against production — WS chat, voice, and affinity all work. Voice costs 80 coins/min.
